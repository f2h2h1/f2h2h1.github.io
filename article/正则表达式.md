# 正则表达式

## 什么是正则表达式

Regular Expression （简称 regexp 或 regex 或 re）

Regular adj. 常规的 规则的 有规律的

Expression n. 表达式

RegExp 的作用是从文本中找出符合规则的内容

常见用途：
- 查找内容：从日志、文本中提取 URL、IP、数字等
- 校验格式：手机号、邮箱、身份证号、日期等
    - 能找出合规则的文本就是符合格式的
- 替换内容：替换符合规则的文本
    - 先找出符合规则的文本然后再替换
    - 纯粹的 RegExp 是没有替换的，替换都是由编程语言或工具实现的

## 正则表达式的发展历史


20 世纪 40 年代，两位神经生理学家 Warren McCulloch 和 Walter Pitts，
研究出了一种用数学方式来描述神经网络的方法，可以将神经系统中的神经元描述成小而简单的自动控制元。
1943年Warren S. McCulloch（神经科学家）与 Walter Pitts（逻辑学家）发表的基础性论文《A Logical Calculus of the Ideas Immanent in Nervous Activity》。


50 年代，一位叫 Stephen Kleene 的数学家在 McCulloch 和 Pitts 早期工作的基础上，发表了《神经网络事件表示法和有穷自动机》 论文。
这篇论文描述了一种叫做 "正则集合（Regular Sets）" 的数学符号，引入了正则表达式的概念。
1951年12月15日由美国兰德公司发布的编号为RM-704的研究备忘录《神经网与有限自动机中的事件表示》，是一篇在计算机科学领域具有里程碑意义的学术报告。在这篇由斯蒂芬·科尔·克莱尼撰写的报告中，首次提出了正则表达式与有限自动机的数学概念。
1956 年收入《Automata Studies》后广泛传播

1968年，肯·汤普逊（Ken Thompson）在《ACM通讯》上发表了 《正则表达式搜索算法》 一文，描述了一种将正则表达式编译为 IBM 7094 机器码、用于在文本中定位匹配字符串的方法。这篇论文所提出的Thompson 构造法，能将正则表达式转换为非确定性有限自动机（NFA），并实现 O(mn)O(mn) 时间的匹配，至今仍是正则引擎的核心算法之一。

汤普逊首先将这一能力植入文本编辑器QED，随后又带入 Unix 的编辑器ed。ed 中有一个命令 g/regular expression/p（全局搜索并打印匹配行），其功能被独立出来，便成了 Unix 中最著名的文本搜索工具 grep——“grep”这个名字本身就来自该命令的缩写。

进入1970年代，Unix 生态中涌现出更多携带正则能力的工具。由于最初的 grep 功能有限，阿尔弗雷德·阿霍（Alfred Aho）开发了增强版的 egrep，引入了 +、? 和更灵活的分组与选择操作。与此同时，sed、awk、lex 等工具也各自实现了正则表达式，但它们支持的语法并不统一，这为后来的标准化埋下了伏笔。


1980年代，POSIX（可移植操作系统接口）标准的出现试图为 Unix 工具中形形色色的正则方言建立共识。POSIX 将正则表达式划分为两个层级：
    BRE（基本正则表达式） ：历史更早的形态，grep、sed、vi 等工具遵循此标准。在 BRE 中，+、?、|、(、) 等符号需要转义后才具备特殊含义。
    ERE（扩展正则表达式） ：作为 BRE 的超集，egrep、awk 等属于此列。元字符无需额外转义即可直接使用，书写上更为简洁。
POSIX 标准在一定程度上统一了 Unix 世界的正则语法，但它所代表的“传统正则”路线，在功能表达力上仍然相对克制。


1986年，Henry Spencer发布了他编写的正则表达式库，这是一个高质量、公开发布的C语言实现
核心算法选择了回溯（backtracking）
这个库迅速被广泛采用，并成为了后来一系列主流正则表达式实现的直接祖先。
今天使用最广的、基于回溯的“慢速”实现——Perl、PCRE、Python 等——其技术血脉都可以追溯到这个1986年的库。

Larry Wall 在 1987 发布了 perl，将正则表达式深度集成到语言中
Larry Wall 在1987年12月18日把1.0版本发布到了comp.sources.misc新闻组。
关于Perl名字的由来，有很多说法。虽然Perl不是正式的首字母缩略词，但仍有各种各样的逆向首字母缩略词，包括“实用的提取和报告语言”。
Perl原名叫“Pearl（珍珠）”。拉里·沃尔想给这个语言起一个有正面意思的短的名字；他考虑了（并且否定了）字典里每一个3—4个字母的词。他也考虑用他的妻子Gloria的名字命名。沃尔在Perl官方发布之前发现了已存在PEARL语言，为了防止混淆，沃尔才把它改名Perl。 
Larry Wall将Spencer的库适配进Perl（1988年），以改进现有正则。

大约在1993年，Henry Spencer根据 POSIX 标准编写了第二个版本的正则表达式库，并捐赠给了 4.4BSD。这个版本实现了 POSIX 1003.2 所定义的正则表达式接口（regcomp、regexec 等），并被描述为 “POSIX.2 兼容”。
在POSIX实现之后，Spencer 又为 Tcl 语言编写了正则表达式引擎，其成果被称为 “高级正则表达式”（Advanced Regular Expressions, ARE）。ARE 的设计目标是在POSIX 1003.2的基础上，吸收一部分Perl 5的扩展特性，从而在保持标准兼容性的同时，获得更强的表达力
ARE 的影响同样深远。PostgreSQL 的正则表达式库就直接继承自 Tcl 的 ARE 实现。
MySQL（在8.0.4之前）也曾使用他的正则表达式库。
Tcl 语言中的高级正则表达式（Advanced Regular Expressions，简称 ARE）是在 1999 年 4 月 30 日 随着 Tcl/Tk 8.1 正式版的发布而首次引入

pcre

    Perl 兼容正则表达式
1997 年，Philip Hazel 为邮件服务器 Exim 开发了 PCRE（Perl Compatible Regular Expressions）

Google于2006年开始使用并最终在2007年开源了RE2引擎，它代表了一种全新的设计理念：“安全第一” 。
RE2完全摒弃了递归回溯，转而采用基于NFA/DFA转换的线性时间算法。

为了应对回溯引擎的性能瓶颈，JIT（即时编译） 技术被引入 PCRE 生态，PCRE-JIT 于2011年出现，显著提升了复杂模式下的执行速度

2015年，PCRE项目推出了PCRE2，它提供了一个经过修订的API，并引入了诸如即时编译等新的性能优化选项

量词 控制匹配次数
    *：匹配前面的元素 0 次或多次
    +：匹配前面的元素 1 次或多次
    ?：匹配前面的元素 0 次或 1 次
    {n}：匹配前面的元素恰好 n 次
    {n,}：匹配前面的元素至少 n 次
    {n,m}：匹配前面的元素至少 n 次，至多 m 次
贪婪匹配与非贪婪匹配
    正则表达式默认是贪婪的，也就是会尽可能匹配最长的字符串。
    在量词后面加上?可以启用非贪婪模式，即尽可能匹配最短的字符串。
    text = "<div>内容1</div><div>内容2</div>"
    # 贪婪匹配：会匹配从第一个<div>到最后一个</div>的整个字符串
    ```python
    greedy_match = re.findall(r'<div>.*</div>', text)
    print(greedy_match)  # 输出: ['<div>内容1</div><div>内容2</div>']
    # 非贪婪匹配：在*后面加?，只匹配到第一个</div>
    non_greedy_match = re.findall(r'<div>.*?</div>', text)
    print(non_greedy_match)  # 输出: ['<div>内容1</div>', '<div>内容2</div>']
    ```
位置匹配：定位字符串中的特定位置
分组与捕获：提取匹配的特定部分

正则表达式有三种基本的运算：
    连接 (Concatenation): ab 表示先匹配 a 再匹配 b。
    并集 (Union): a|b 表示匹配 a 或者 b。
    闭包 (Kleene Star): a* 表示匹配 0 个或多个 a。
其它常见的符号如 +, ?, [] 都可以由这三种基本运算推导出来：
    a+ 等价于 aa*
    a? 等价于 a|ε (ε 表示空串)

DFA 与 NFA 的对比
    NFA 引擎：Perl, Python, Java, Ruby 等大多数语言的正则库。支持反向引用等高级特性，但可能出现回溯导致的性能问题（ReDoS）。
    DFA 引擎：awk, egrep, lex。速度极快，但不支持反向引用等特性。
RE2 算法
    在工业界，正则表达式引擎的性能至关重要。
    传统的正则引擎（如 PCRE, Python re, Java Pattern）大多基于回溯（Backtracking）算法。
    虽然支持丰富的功能（如反向引用），但在某些情况下会出现指数级的时间复杂度，导致 ReDoS（正则表达式拒绝服务攻击）。
    Google 的 RE2 算法正是为了解决这个问题而诞生的。
    它由 Russ Cox 开发，被 Go 语言标准库采用。

哪些可以匹配？ (正则语言)
只要一个问题只需要有限的内存来记录当前的状态，它通常就可以用正则表达式解决。
    固定模式：如关键词查找 hello。
    有限的重复：如 a{5} (5个a)。
    不确定的重复：如 a* (任意个a)。
    有限的选择：如 a|b。
    有限长度的上下文：如“后面跟着数字的字母”。
哪些不能匹配？ (非正则语言)
最典型的例子是：任意深度的嵌套结构。
    配对的括号
    回文串
    算术表达式：如 ((1+2)*3)，因为涉及任意深度的括号嵌套。
    HTML/XML 解析：虽然可以用正则匹配简单的 <div>...</div>，但无法处理嵌套的 <div><div>...</div></div>。
结论
    能用正则：词法分析（Token识别）、简单的格式校验（邮箱、日期）、扁平的文本搜索。
    不能用正则：语法分析（解析代码结构）、处理嵌套括号、解析 HTML/XML/JSON。
对于嵌套结构，请使用解析器 (Parser)，不要试图用正则表达式去“强行”匹配。

正则表达式在计算机科学中，是指一个用来描述或者匹配一系列符合某个句法规则的字符串的单个字符串。
在很多文本编辑器或其他工具里，正则表达式通常被用来检索和/或替换那些符合某个模式的文本内容。
正则表达式这个概念最初是由Unix中的工具软件（例如sed和grep）普及开的。
正则表达式通常缩写成“regex”，单数有regexp、regex，复数有regexps、regexes、regexen。

正则表达式零宽断言
(?=exp)	 零宽度 正向 先行 断言(zero-width positive lookahead assertion)，它断言自身出现的位置的后面能匹配表达式 exp 。
(?<=exp) 零宽度 正向 后行 断言(zero-width positive lookbehind assertion)，它断言自身出现的位置的前面能匹配表达式 exp 。
(?!exp)	 零宽度 负向 先行 断言(zero-width negative lookahead assertion)，它断言此位置的后面不能匹配表达式 exp 。
(?<!exp) 零宽度 负向 后行 断言(zero-width negative lookbehind assertion)，它断言此位置的前面不能匹配表达式 exp 。

断言用来声明一个应该为真的事实。正则表达式中只有当断言为真时才会继续进行匹配。


(exp) ：目标字符串需要匹配exp,并将该分组匹配的子文本保存到自动命名的组里；
(?<name>exp)：目标字符串需要匹配exp,并将该分组匹配的子文本保存到名称为name的组里

不捕获
    不捕获就是在分组的前边加上?:，可以在不需要捕获分组的表达式中使用，加快表达式执行速度。
    就拿匹配<title>xxx</title>标签来说，通过分组可以简写为
    <(title)>.*</\1> 
    但是如果是(?:title),则\1就不能捕获到这个子组了，只能捕获第一个出现的非?:的分组作为\1
    同时注意(?:title)本身会在完整匹配中，只是不在子组中，注意和断言的区别
断言
    所谓断言，就是指明某个字符串前边或者后边，将会出现满足某种规律的字符串。
    就拿匹配<title>xxx</title>标签来说，我们想要的是xxx，它没有规律，但是它前边肯定会有<title>，后边肯定会有</title>，这就足够了。
    想指定xxx前肯定会出现<title>，就用正后发断言，表达式：(?<=<title>).*
    想指定xxx后边肯定会出现</title>，就用正先行断言，表达式：.*(?=</title>)
    两个加在一起，就是(?<=<title>).*(?=</title>)
    这样就能匹配到xxx，匹配的内容不包括断言的内容，即完整的匹配就是xxx，不会包含<title>和</title>,子组中也不包含。
对正后发和正先行的解释：
    其实掌握了规律，就很简单了，无论是先行还是后发，都是相对于xxx而言的，也就是相对于目标字符串而言。
    假如目标字符串后边有条件，可以理解为目标字符串在前，就用先行断言，放在目标字符串之后。
    假如目标字符串前边有条件，可以理解为目标字符串在后，就用后发断言，放在目标字符串之前。
    假如指定满足某个条件，就是正。
    假如指定不满足某个条件，就是负。
    断言只是条件，帮你找到真正需要的字符串，本身并不会匹配！

常见字符串搜索算法
    暴力匹配算法 (Brute Force, BF)：
        最直观的方法，从文本串头部开始逐个字符对比。匹配失败时，模式串向右移动一位，文本串指针回溯。时间复杂度为 \(O(m \times n)\)（其中 n 为文本长度，m 为模式串长度）。
    KMP 算法 (Knuth-Morris-Pratt)：
        利用匹配失败后的已知信息，通过构建 Next 数组（最长公共前后缀）跳过已经匹配的字符。避免了指针回溯，匹配时间复杂度优化至 O(m + n)。 
    Boyer-Moore 算法 (BM)：
        实际应用中效率极高的高效算法（如文本编辑器查找、Grep 命令多采用此法）。采用从右向左的比较方式，并运用坏字符规则与好后缀规则跳过大量无法匹配的字符。搜索关键字越长，速度越快。 
    Sunday 算法：
        另一种从左向右匹配但按右侧对齐优化的算法。发生不匹配时，根据文本串中参与匹配的最右侧字符的下一个字符在模式串中的位置来决定跳跃距离，实现简单且速度极快。
